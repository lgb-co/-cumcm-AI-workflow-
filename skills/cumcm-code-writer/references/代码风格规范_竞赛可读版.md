# 代码风格规范（竞赛可读版）

> 目标：让评委在附录里能顺着代码读懂“哪一段对应论文哪一问、哪个公式”，同时保证换台电脑能跑出同样的结果。
> 一句话标准：**结构直白、命名对得上公式、随机可控、结果可复现**。

## 一、项目组织

```text
code/
├── data/                  # 输入数据（原始数据只读，清洗结果另存）
├── common/                # 公共函数：数据读取、标准化、绘图、指标计算
├── q1_<问名>.py           # 逐问脚本，命名与论文小节编号一致
├── q2_<问名>.py
├── run_all.py             # 顺序调用各问，产出全部结果
├── config.py              # 路径、随机种子、参数集中在这里
└── requirements.txt       # 依赖清单（含版本）
```

MATLAB 版本用同样的分层，入口 `run_all.m`，公共函数放 `common/`。一个问一个入口文件，便于附录里对齐“第 4.1 节 / q1_评价模型.py”。

## 二、命名与注释

- 变量名尽量用论文符号的拼音或英文对应：`x_ij`、`w_entropy`、`y_hat`；避免 `a1`、`tmp2`、`data2`。
- 函数名用动词短语：`normalize_positive`、`solve_transport`、`plot_sensitivity`。
- 注释只写两类：
  1. 公式或符号对应，例如 `# 式(4-2)：正向化后的决策矩阵 R_ij`；
  2. 非显然的算法步骤与参数来源，例如 `# ρ=0.5：分辨系数，按惯例取值，敏感性见第 5.3 节`。
- 不写“初始化变量”“循环所有行”“返回结果”这类从代码本身就能看出的注释。
- 不写与实现不符的注释；改代码同时改注释。

## 三、参数与随机性

- 所有可调参数集中到 `config.py`，脚本里不散落魔法数字。
- 随机算法在入口处固定种子并把种子写入结果文件表头，例如 `seed=42`；第三轮自测会换成多个种子重跑。
- 迭代类算法记录收敛过程（目标值序列、最优个体变化），并输出收敛曲线数据。
- 任何“人工设定”的参数都要在结果文档里写清来源：题给、文献、经验值或标定得到。

## 四、数据读写

- 原始数据只读：程序不覆盖 `data/` 下的原始文件；清洗结果写 `work/<项目名>/clean/`。
- 读 Excel/CSV 时显式指定编码与表头，遇到中文列名不要靠索引硬取，按列名取并在缺失时报错。
- 输出文件统一带表头与单位，例如 `最优方案_万元.csv`，数值保留位数与论文一致。
- 图表数据与绘图脚本分离：先存 `tables/` 或 `figures/*.csv`，再画图，保证换风格不改数值。

## 五、异常与校验

- 保留最小必要的校验：输入维度、行数、缺失率、约束可行性；报错信息写清“哪一行数据、期望什么、实际什么”。
- 不用整段 `try/except: pass`；不要用异常处理掩盖数据问题——跑不出来要让用户看到。
- 约束不可行、模型不收敛、样本不足这类情况必须有明确输出，并在结果文档里作为限制说明。

## 六、可复现要求

- `requirements.txt` 记录版本；结果文档里附 Python/MATLAB 版本与关键库版本。
- `run_all.py` 一条命令重现全部结果，运行时间在结果文档里注明。
- 路径全部相对项目根目录，禁止硬编码 `D:\...` 这类本机绝对路径。
- 中间产物命名稳定，重跑覆盖而不是生成 `结果_final_v2.csv` 这类文件。

## 七、附录友好要求

- 单文件不要超过约 300 行；超了拆模块，附录按“入口 → 各问 → 公共函数”顺序列出。
- 每个脚本开头写明：对应哪一问、输入什么文件、输出什么文件、怎么运行。
- 不引入没用到的第三方库；引入的库必须能通过 `requirements.txt` 装上。
- 附录中的代码与工程目录逐字一致（`build_appendix.py` 会做哈希校对）。
