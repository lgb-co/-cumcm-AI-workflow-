# 低 AI 味代码规范

> 用途：让交付代码读起来像参赛队自己写的，而不是某种模板批量生成的。
> 注意：这里的“低 AI 味”不是让人看不懂，而是去掉机械对称、过度注释、过度防御和空洞命名。

## 一、四个典型 AI 味特征

| 特征 | 表现 | 为什么不好 |
|---|---|---|
| 过度注释 | 每行都有注释，注释复述代码 | 附录篇幅被稀释，真正关键说明被淹没 |
| 机械对称 | 每个函数都 `try/except`，每个循环都带 `if not data` | 读起来冗余，掩盖真实数据问题 |
| 空洞命名 | `data1`、`result_final`、`process_data_function` | 看不出与公式的对应关系 |
| 模板话术 | 输出日志写 “Successfully completed the task!”、脚本头写大段版权方框 | 与数模写作场景不符 |

## 二、应当保留的“人味”

- 有取舍的注释：只解释为什么这么做，特别是参数来源与近似理由。
- 具体的过程输出：跑的时候打印关键中间量，如“第 3 次迭代目标值 1234.5”。
- 与论文呼应的命名与图号：变量名和公式符号一致，图文件名带题号，如 `fig_4_2_收敛曲线.png`。
- 合理的工程细节：随机种子、数据校验、结果表头、运行时间记录——这些评委看得见、也加分。

## 三、正反例对照

| 别写 | 写成 |
|---|---|
| `# 对数据进行标准化处理` 紧跟在 `X = (X - X.mean())/X.std()` 上一行 | 删掉注释；在函数文档里写清用的是 Z-Score 与为什么不用极差标准化 |
| 每个函数都套 `try: ... except Exception as e: print(e)` | 只在真正的边界处校验，并抛出具名错误：`raise ValueError(f"决策矩阵列数应为 {n}，实际 {X.shape[1]}")` |
| `result_final_v2_revised.csv` | `topsis_排序结果.csv` |
| 打印 `===== 开始执行 =====`、`任务完成！` | 打印 `样本数=120，指标数=8，CR=0.042` 这类有信息量的数字 |
| 所有参数写在脚本里且命名为 `alpha = 0.5  # 参数` | 把参数集中到 `config.py`，注释写 `ALPHA = 0.5  # 式(3-4) 平滑系数，按第 5.2 节敏感性分析取 0.5` |
| 为了“通用”写三层抽象类与工厂模式 | 直接写函数；本题只用一种方法就不需要抽象层 |
| 图表标题写 `Figure 1: The result of the analysis` | 中文图题写 `图 4-1 各方案综合得分对比（权重由熵权法确定）` |

## 四、自检清单（交付前逐条过）

- [ ] 每个脚本开头 3–6 行说清：对应哪一问、输入、输出、运行命令。
- [ ] 没有复述代码的注释；每条保留的注释都能回答“为什么”。
- [ ] 没有 `except: pass`、没有吞掉异常的包装。
- [ ] 变量名与论文符号一致，没有 `tmp`、`data2`、`最终结果`这类名字。
- [ ] 打印信息包含具体数字，不写“开始/完成/成功”这类空话。
- [ ] 随机算法有固定种子，且种子写在结果文件里。
- [ ] 没有硬编码的绝对路径、没有写死的结果数值。
- [ ] 结果文件名能自解释，包含单位或口径。

## 五、与报告写作规范的衔接

代码注释与结果文档使用同一套语气：直接给事实和数字，不堆形容词。结果文档的写作规则沿用 `代码编写评价/references/报告写作风格_自然专业.md` 的硬约束（禁套话、一句话一件事、结论贴证据）。
