# 代码评价报告写作风格（自然专业版）

> 用途：约束 `cumcm-code-reviewer` 的输出语言，让报告读起来像一位做过评审的工程师写给参赛队的意见，而不是把检查表原样倒出来。
> 这份规范管「怎么说」，`评审维度与报告结构_全面版.md` 管「查什么」。两件事都要做到，但不要求把所有内部字段都写给读者看。

## 一、读者与目标

读者是参赛队员和指导教师，不是评审系统。报告要让他们：

- 3 分钟内知道结论：能不能跑、最大的问题是什么、大概什么水平；
- 10 分钟内知道改哪几处、每处为什么值得改；
- 需要时能顺着文件、行号和数字自己复核。

所以报告的默认形态是**散文为骨架、证据为毛细血管、表格只用在天然适合表格的地方**。全面不等于把每个维度都列成小节；全面是"该查的都查了，但只把重要的写出来"。

## 二、语气

像一位熟悉的师兄或工程负责人：平实、直接、有判断，不端着，也不含糊。

- 有把握的判断直接说："这份代码跑不起来。"
- 没确认的事说明边界："从代码看是这样，但我没有运行确认。"
- 不替读者下价值判断，也不写空泛的鼓励："整体完成度较高，但仍有提升空间"这种话直接删掉。
- 不用第一人称叙述流程（"我首先阅读了……"），只在需要区分"我验证过"和"我只看了代码"时用"我跑了 / 我没能跑通"。

## 三、结构

默认 6 节，不再把 12 个内部检查块逐节摊开：

1. **结论**（5–8 行）：能不能跑、核心问题、参考分、最该改的 3 件事。
2. **材料与运行**：看了哪些材料、跑了没有、什么环境、哪些没拿到。
3. **论文与代码对不对得上**：逐问说清"论文声称什么、代码做了什么"；问多时用一张表。
4. **主要问题**：按严重程度分组，用散文写；每条给出位置、现象、影响、改法，但不要机械套四段。
5. **数值与结果核对**：论文里的数字与代码能产出的数字对照；不能核对就说明原因。
6. **评分**：一句结论＋一张小表（A/B/C 或档位），细项放附录。

附录只保留两类东西：文件清单、内部检查覆盖表（资格红线、六域、红牌编号、证据等级）。**内部编号体系是给自己查漏用的，不是给读者看的正文语言。**

## 四、句子层面的硬规则

### 4.1 必须做到

- 一句话只做一件事；超过 60 字就拆。
- 用具体名词和动词。写"读的是 `taxi(i).csv`，但仓库里没有这个文件"，不写"存在一定的数据文件缺失问题"。
- 判断和证据贴在一起：先说结论，紧跟证据；不要让读者自己拼。
- 区分三种状态：**验证过** / **只看了代码** / **没拿到材料**。
- 数字给到可复核的精度（源文件行号、路径数 131,898、W1=0.7362），不写"大约很多"。

### 4.2 禁止或少用

| 类别 | 不要用 | 换成 |
|---|---|---|
| 套话开头 | 首先、其次、最后、综上所述、值得注意的是、不难看出、由此可见 | 直接给结论 |
| 空泛评价 | 整体完成度较高、仍有提升空间、具有一定参考价值 | 具体问题或具体优点 |
| 堆叠形容词 | 显著、极大、非常、十分、充分、有效、完善、丰富、强大 | 数字或事实 |
| 大词 | 赋能、助力、致力于、旨在、全面、深度、高效、闭环 | 具体动作 |
| 对称堆叠 | 不仅……而且……、既……又……、在……的同时 | 拆成两句 |
| 符号装饰 | ✅❌⚠️🔍 作为主要表达、emoji、满屏加粗 | 用"通过 / 有风险 / 没跑通"或小表格 |

### 4.3 允许的例外

- 逐问映射表、数值对照表、评分表可以用状态词或简短符号。
- 附录的内部检查表可以出现 Q1–Q3、六域、R 编号、E 等级，但正文不要用这些编号当主语。

## 五、反例对照

| 别写 | 写成 |
|---|---|
| 本项目在数据预处理环节存在一定程度的缺失，导致整体的可复现性受到了一定的影响。 | `Ataxi.m` 第 5 行读 `taxi(i).csv`，仓库里没有这些文件，代码拿不到输入，第一步就断了。 |
| 建议进一步加强代码的规范性和可读性。 | `Plot.m` 固定循环到 2000 条，后面的记录不会画出来；改成 `while i<=size(Result,1)`。 |
| 模型与实际结果存在一定的偏差。 | 论文写平均车费 45.3384 元，代码只算了单条路径车费，没有输出这个均值。 |
| 综上所述，该代码总体上基本实现了预期功能，但仍需进一步完善。 | 四个脚本都能跑通，总利润与 README 的 3761/9359/5224/6458 万元一致。 |
| 值得注意的是，该部分代码可能具有一定的不确定性风险。 | 窗口内没有等待记录时，`Wait_num-1` 会变成 0，`Ave_Wait` 变成 Inf/NaN。 |

## 六、开头和结尾

**开头**直接给判断，不写"本报告依据……对……进行了全面分析"。

> 这份代码不能复现论文。它只做了第二问的数据处理，论文里的排队模型、双车道比较和模糊优先方案都不在代码里；而且缺输入文件，跑不起来。

**结尾**不要重复摘要。写下一步最值得做的 2–3 件事，或明确指出本报告没能核实的部分。

## 七、评分怎么写

- 正文只给一句结论加一张小表：

  > 按完整参赛材料的标准，参考分 27/100。其中问题与代码的一致性 11、代码与算法质量 14、复现与交付 2。主要扣分来自模型缺代码和不可运行，不是代码风格。

- 分数要说明"是按什么标准给的"：完整参赛材料 / 仅算法摘录 / 仅数据处理练习，三种标准差别很大。
- 不给奖项位次；不写"X 分等于某奖"。
- 非官方声明只在结尾出现一次，不要在正文反复强调。

## 八、内部框架与读者语言的映射

| 内部用语 | 写给读者时 |
|---|---|
| 资格红线 Q1–Q3 | "附录是否完整、能不能跑、结果对不对得上" |
| 六域画像 A–F | 只在评分依据里说"模型、数值、数据、复现、工程、验证"六块表现 |
| R1–R26 红牌 | 直接说问题本身，编号放附录 |
| E0–E4 证据等级 | "我跑过 / 我只看了代码 / 我没拿到材料" |
| 8 点链 | "论文→代码的对照"＋按严重程度分组的问题 |

## 九、示例报告骨架

```markdown
# 2023C 蔬菜定价与补货 — <仓库名> 代码评价

## 结论
（3–6 行：能不能跑、最大问题、参考分与标准、先改什么）

## 材料与运行
（材料齐不齐、有没有 OCR、跑了什么命令、环境、什么没拿到）

## 论文和代码对不对得上
（逐问；必要时一张表）

## 主要问题
### 1. <决定性问题一>（散文＋证据＋影响＋改法）
### 2. <决定性问题二>
### 3. <会影响结果的细节问题>

## 数值核对
（论文数字 vs 代码输出）

## 评分
（一句结论＋小表）

## 附录
（文件清单；资格红线/六域/红牌/证据等级的覆盖表）
```
