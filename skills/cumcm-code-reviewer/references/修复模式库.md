# 代码评价 · 修复模式库

> 用途：写《改进建议报告》时，按问题类型套用这里的修复步骤与验收方法，避免每条建议从零想。
> 用法：先在检测报告里给问题定级（P0/P1/P2）与编号，再到本库找对应模式，按项目实际情况改写成具体步骤。
> 依据：官方《论文格式规范（2026 修订稿）》；Google Engineering Practices；Conventional Comments；GitHub 文档；JOSS review checklist；rOpenSci reviewer guide；The Turing Way / ReproHack；CliMA DeveloperGuides；PEP 8。原始快照见 `训练语料/references_sources/improvement/`。

每个模式包含：适用症状（含红牌/资格红线）→ 修复步骤 → 验收方法 → 常见坑 → 参考依据。

## 一、资格与交付

### M01 附录/支撑材料缺完整可运行源程序（Q1、D4）

适用症状：只有部分问题的代码；只交结果文件；代码只在作者机器上存在；附录没有文件列表。

修复步骤：
1. 按赛题小问逐条列出应有的源文件与结果文件，形成支撑材料清单。
2. 把缺的问补成可独立运行的脚本或函数，入口统一。
3. 把清单写进论文附录，文件名与实际文件一致。
4. 把原始数据、中间产物、结果文件分目录归位。

验收方法：按附录清单逐个打开，确认每个小问都有对应源程序；在干净目录能按说明跑通。

常见坑：用截图代替代码；把多个问题的代码塞进一个无法定位的文件；清单与实际文件不一致。

参考依据：官方 2026 格式规范第五条、第十一条。

### M02 缺题目要求的交付文件（R7、R16、R25、C4、Q3）

适用症状：题目要 result*.xlsx / 附件 A、B，仓库里没有；代码只输出 CSV 或控制台；覆盖了原模板。

修复步骤：
1. 把题目的交付要求逐条抄成清单（文件名、格式、列、单位、小数位）。
2. 在代码里增加独立导出步骤，读取计算结果写入模板。
3. 保留原始模板，输出到新文件，按题目规定的文件名命名。
4. 导出后做一次列名、行数、单位、小数位核对。

验收方法：运行后出现题目要求的全部文件；用模板逐列比对，数值可追溯到代码输出。

常见坑：只导出一个文件；改了列顺序；把结果写到中间目录而不是题目要求的位置。

参考依据：官方 2026 格式规范第五条；题目原文的交付要求。

### M03 代码结果与论文数值对不上（R12、F8、Q3）

适用症状：论文有具体数值，代码没有对应输出；或代码输出与论文数值不同。

修复步骤：
1. 把论文里的关键数值做成一张对照表（页码/表号、数值、单位）。
2. 在代码里找到该数值的产生位置，确认口径（时点、单位、平均方式）。
3. 把代码输出写成文件，逐项与论文对照；不一致时先查参数与口径，再查算法。
4. 修改论文或代码中的错误一方，并在报告中记录差异原因。

验收方法：对照表每一行都能由代码输出直接得到；差异为零或在论文声明的误差范围内。

常见坑：只对总量不对分项；把“约等于”当成一致；改了代码却不更新论文。

参考依据：官方 2026 格式规范第五条；CliMA DeveloperGuides（数学与文档一致性）。

### M04 支撑材料与论文内容不符（R26、Q1）

适用症状：支撑材料里有多套互相矛盾的代码/结果；论文描述的方法与代码不一致。

修复步骤：
1. 确认论文最终采用的方法与参数版本。
2. 把其余实验版本移到“实验/废弃”目录，不放进正式支撑材料。
3. 更新 README 与附录清单，只保留与论文一致的版本。
4. 重新跑一遍最终版本，确认结果与论文一致。

验收方法：支撑材料里只有一套与论文一致的实现；附录清单与文件一一对应。

常见坑：把多版结果都放在支撑材料里让评委自己猜；旧版本文件名更显眼。

参考依据：官方 2026 格式规范第十一条。

## 二、复现与环境

### M05 随机算法没有固定种子（R1、B5）

适用症状：GA/PSO/SA、蒙特卡洛、随机森林、模拟等每次运行结果不同。

修复步骤：
1. 在程序入口固定随机种子，覆盖所用库（Python 的 random/numpy/框架各自设置）。
2. 把种子写进配置或命令行参数，并在 README 说明默认值。
3. 对随机算法跑多次，报告结果的波动范围或均值±标准差。
4. 在论文中说明随机性与稳定性结论。

验收方法：同一命令连续运行两次结果一致；多次运行报告给出波动范围。

常见坑：只固定了一个库的种子；多进程/GPU 下种子失效；子脚本各自重置种子。

参考依据：PEP 8 可读性要求；The Turing Way（复现）；CliMA DeveloperGuides（可复现性）。

### M06 缺依赖与环境说明（R2、R21、D1）

适用症状：只有代码，没有 requirements/environment/工具箱说明；别人装不上。

修复步骤：
1. 列出语言版本、关键库及版本、外部工具与工具箱。
2. Python 生成 requirements（或在 README 写安装命令）；MATLAB 写明所需 Toolbox。
3. 写清运行顺序与工作目录。
4. 在一台干净环境里按说明走一遍，把遇到的问题补进文档。

验收方法：新环境按 README 一次装好并跑通。

常见坑：只写“需要 numpy/pandas”不写版本；MATLAB 代码用了 Mapping/Statistics Toolbox 却不写。

参考依据：JOSS review checklist（安装与文档）；The Turing Way（安装）。

### M07 输出目录不存在导致首次运行失败（R17、D2）

适用症状：代码写结果到 verify/、output/ 等目录，但目录没创建。

修复步骤：
1. 在入口检查输出目录，不存在就创建。
2. 把输出路径集中到配置，不散落在各脚本。
3. 结果目录纳入交付说明，必要时保留一份空目录或 .gitkeep。

验收方法：删除输出目录后运行，程序自动创建并正常写出结果。

常见坑：只在自己机器上存在该目录；用绝对路径写死输出。

参考依据：PEP 8；通用工程实践。

### M08 绝对路径与机器特定配置（R19、D3）

适用症状：代码里出现 D:\...、/home/...、/Users/...；依赖仓库外文件。

修复步骤：
1. 把所有输入/输出路径改成相对路径或配置项。
2. 相对路径以项目根或脚本目录为基准，写清运行目录。
3. 把机器特定配置移出代码，放进配置文件的默认值。
4. 在干净目录验证。

验收方法：换个路径运行结果不变；代码中检索不到本机绝对路径。

常见坑：相对路径依赖“当前目录”，换目录就断；只改了部分脚本。

参考依据：PEP 8；JOSS review checklist。

### M09 数据入口缺失、中间数据无生成脚本（R20、C1）

适用症状：代码读 taxi(*).csv、info.xlsx 等文件，但仓库没有；中间 JSON/CSV 不知从何而来。

修复步骤：
1. 梳理“原始附件 → 中间数据 → 结果”的完整链路，画一张数据流清单。
2. 把每一步的生成脚本补齐，或让主脚本直接从原始附件读取。
3. 中间数据可保留，但必须能由脚本重新生成。
4. 在 README 写清数据获取方式与生成顺序。

验收方法：只提供官方附件的情况下，能按说明生成全部中间数据并跑通。

常见坑：把预处理脚本当成“不重要”删掉；中间文件名与代码里的不一致；依赖外部下载却不写地址。

参考依据：官方 2026 格式规范第十一条；The Turing Way（可获取与复现）。

### M10 MATLAB 工具箱与版本未记录（R14、D1）

适用症状：代码用了 Mapping/Statistics/Optimization 等工具箱，但不说明。

修复步骤：
1. 检索代码调用的非基础函数，逐个标注所属工具箱。
2. 在 README 写明 MATLAB 版本与工具箱清单。
3. 尽量用基础函数替代非必要工具箱（可选）。

验收方法：在只装了说明中工具箱的环境里能跑通。

常见坑：作者环境装了全套工具箱，别人没有；用旧版语法在新版本报错。

参考依据：MathWorks Code Analyzer（官方页本次访问受限，按通用 MATLAB 实践执行）；JOSS review checklist。

## 三、正确性与数值

### M11 时间/范围/规模覆盖不足

适用症状：题目要 0–300 s，代码只算 0–150 s；要 −100–100 s 只算到 50 s；要全量数据只用了抽样。

修复步骤：
1. 把题目的时间/范围/规模要求写成数字清单。
2. 在循环上界、步长、数据筛选处逐项对照，改成满足要求的取值。
3. 输出后统计时间列数/样本数，和清单核对。

验收方法：输出列数或样本数等于题目要求（如 301 列、201 列）。

常见坑：为了跑得快私自缩短范围；步长用了 10 s 而非 1 s；只在论文里补全数值而代码不变。

参考依据：赛题原文；官方 2026 格式规范第五条。

### M12 关键数值硬编码（R18、R3）

适用症状：上一问的结果被写死进下一问；代码里的答案不是算出来的。

修复步骤：
1. 找出所有直接写成答案的数值，确认它应由哪一步计算。
2. 把该数值改为由上一步的输出文件或函数返回值传入。
3. 保留参数默认值时也必须注明来源与适用范围。
4. 重新运行全流程，确认最终答案由搜索/求解产生。

验收方法：修改上游输入后，下游结果随之变化；日志能看到求解过程。

常见坑：只把注释改成“来自问题二”，值仍写死；搜索代码被注释掉，只有画图入口。

参考依据：CliMA DeveloperGuides（公式与代码一致）；官方 2026 格式规范第五条。

### M13 除零、空切片、边界与极端输入（R9、B2、B4）

适用症状：分母可能是 0；空数组求均值/方差；负值开根号；浮点相等比较；迭代不收敛。

修复步骤：
1. 列出所有可能为 0 或空的分母、切片、集合。
2. 加显式判断：计数不足时跳过、记 0 或给出警告，不让结果变成 Inf/NaN。
3. 对零输入、单元素、极值做一次小规模测试。
4. 在日志里输出被跳过的窗口数量。

验收方法：构造空/单元素/极值输入，程序不产生 Inf/NaN，且给出明确提示。

常见坑：用 try/except 静默吞掉；用均值填充掩盖问题；只测了正常数据。

参考依据：CliMA DeveloperGuides（数值稳健性）；PEP 8。

### M14 魔法数与参数无来源（R3、A3）

适用症状：费率、阈值、上限直接写死在代码里，无注释。

修复步骤：
1. 把常量集中到配置文件或参数区。
2. 每个常量标注来源（题目附录、官方费率、论文公式、数据拟合）。
3. 对拟合得到的参数说明拟合数据与误差。

验收方法：任意常量都能指回题目、论文或数据；换题时只需改配置。

常见坑：把拟合参数当成物理常量；同一常量在多处取值不一致。

参考依据：PEP 8；CliMA DeveloperGuides（常数与引用一致性）。

### M15 目标/符号/口径错误（R5、R8）

适用症状：max 当 min；损耗率、成本加成、工作日/双休等口径与题目不符。

修复步骤：
1. 把题目与论文的关键口径写成对照表。
2. 在目标函数、约束、数据筛选处逐项核对符号与定义。
3. 用一个小规模算例验证方向（增大参数结果应往哪边走）。

验收方法：小算例下结果方向符合业务/数学预期；对照表无差异。

常见坑：只改目标函数忘了约束；单位换了口径没换。

参考依据：赛题原文；CliMA DeveloperGuides（数学与物理正确性）。

### M16 论文承诺的模型没有进代码（R6、R11、F7）

适用症状：论文写 M/M/1、整数规划、模糊评价等，代码里找不到实现。

修复步骤：
1. 把论文每问声称的模型、公式、参数列成清单。
2. 在代码里逐个找对应实现；缺的补成函数或脚本。
3. 让每个模型都有可运行入口与输出。
4. 用论文中的算例或小规模数据验证输出。

验收方法：论文每个模型都能在代码里定位到实现并运行出对应结果。

常见坑：用注释声称“已实现”；只实现了数据预处理；模型被简化却不说明。

参考依据：官方 2026 格式规范第五条；CliMA DeveloperGuides（公式与文档一致）。

### M17 收敛、采样与误差没有依据（R22、F10）

适用症状：蒙特卡洛样本数、网格步长、迭代次数是随手定的，没有收敛或误差分析。

修复步骤：
1. 列出所有影响精度的参数（步长、样本数、迭代上限、容差）。
2. 做一次参数扫描，记录结果随参数变化的曲线。
3. 选择结果稳定的区间作为最终参数，并写进论文。

验收方法：扫描曲线显示所选参数位于稳定区间；报告中给出误差量级。

常见坑：只跑一个参数值；用“跑得快”作为选参理由。

参考依据：CliMA DeveloperGuides（近似精度与收敛研究）。

## 四、工程质量

### M18 复制粘贴与多版本目录（R4、R13）

适用症状：同一算法多份拷贝；code/ 与 support/、最终/ 与 辅助/ 并存。

修复步骤：
1. 找出重复实现，确认哪一份是最终版本。
2. 抽出公共函数/模块，其余调用同一份实现。
3. 把历史版本移到归档目录，不进正式支撑材料。

验收方法：同一算法的实现只有一处；修改后所有调用点一致。

常见坑：只抽了函数不改调用；归档目录仍被打包进支撑材料。

参考依据：PEP 8；Google Engineering Practices（复杂度与设计）。

### M19 调试输出与死代码残留（R24）

适用症状：大量 print、注释掉的代码、临时脚本、写死的调试文件。

修复步骤：
1. 把必要的运行信息改为分级日志，去掉调试打印。
2. 删除注释掉的旧实现（历史版本交给版本控制）。
3. 清理临时文件与硬编码的调试路径。

验收方法：正常运行只输出关键进度与结果；代码中无成段注释代码。

常见坑：把 print 改成注释但仍留在文件里；日志刷屏。

参考依据：PEP 8；Google Engineering Practices（注释与风格）。

### M20 性能与规模问题（E4）

适用症状：多重循环、重复读大文件、每步重算常数、内存爆掉或超时。

修复步骤：
1. 定位耗时的循环与重复计算，测量基线时间与内存。
2. 改为向量化/预计算/缓存，或调整数据分块。
3. 重新测量并记录前后对比。

验收方法：运行时间与内存显著下降，结果与改前一致。

常见坑：优化后结果变了；只在小数据上验证。

参考依据：PEP 8；CliMA DeveloperGuides（性能规则）。

## 五、验证与测试

### M21 没有测试、自检或基准（F1、F2、R23）

适用症状：唯一的“验证”是程序能跑完；没有单元检查，也没有解析解/基准对比。

修复步骤：
1. 为关键函数写最小自检（输入已知、输出可预期）。
2. 用解析解、简单算例或文献值做一次对比，记录误差。
3. 把检查脚本与结果写进支撑材料。

验收方法：自检脚本可一键运行并给出通过/失败；基准对比给出误差。

常见坑：测试只覆盖主路径；用同一套代码生成“基准”。

参考依据：JOSS review checklist（功能与文档）；CliMA DeveloperGuides（验证）。

### M22 没有敏感性/稳定性分析（F3、R23）

适用症状：参数扰动、多初值、多情景下结论是否稳定完全没提。

修复步骤：
1. 选出对结果影响最大的 3–5 个参数。
2. 在合理范围内扰动，记录结果变化。
3. 给出结论稳定区间与失效边界，写进论文。

验收方法：报告中有扰动曲线或区间，能说明结论对参数的依赖。

常见坑：只扰动一个参数；扰动范围不写依据。

参考依据：官方评阅要点（敏感性）；JOSS review checklist。
