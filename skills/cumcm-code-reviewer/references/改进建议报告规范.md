# 代码评价 · 改进建议报告规范

> 用途：定义 `cumcm-code-reviewer` 的第三份产物——`<名称>_改进建议报告.md`。检测报告回答“有什么问题”，改进建议报告回答“具体怎么改、改完怎么确认”。
> 适用：所有需要代码评价的场景（CUMCM/研赛/美赛/校赛/自定义题）。
> 依据：官方《论文格式规范（2026 修订稿）》；Google Engineering Practices（如何写评审意见）；Conventional Comments（标签与阻断级别）；GitHub 文档（suggested changes、范围外建议转 issue）；JOSS review checklist；rOpenSci reviewer guide；The Turing Way / ReproHack；CliMA DeveloperGuides；PEP 8。原始快照见 `训练语料/references_sources/improvement/`（不随插件分发）。

## 一、什么时候生成

- 检测报告里出现 **P0 或 P1** 问题时，生成改进建议报告。
- 只有 P2 或没有问题时，**不生成**；在检测报告末尾写一句“无 P0/P1，未生成改进建议报告”。
- 材料不全、只做初步检查时，不生成正式改进建议报告；如用户坚持，标题必须标“初步”。
- 两份报告都写入选定基础路径下的 `代码评价/` 文件夹（不存在则创建，已存在则复用）；文件名分别为 `<名称>_代码检测报告.md`（或 `_代码评价报告.md`）与 `<名称>_改进建议报告.md`；同名文件已存在时追加 `-2`、`-3` 后缀，不覆盖旧报告。

## 二、与检测报告的关系

- 编号完全沿用检测报告：P0-1、P1-2、P2-3，一一对应，方便两份报告对着看。
- 每条建议开头先复述该问题的一句话结论，再给修复步骤；不要要求读者回去翻检测报告才能看懂。
- 不新增检测报告里没有的问题；如修复过程中发现新问题，回到检测报告补录后再写进改进报告。
- 评分逻辑不受影响；改进报告不改变 A/B/C 分数。

## 三、每条建议的固定字段

| 字段 | 写法要求 |
|---|---|
| 编号 | 沿用检测报告编号（如 P0-1） |
| 标签 | 阻断 / 非阻断；并用一句类别词（正确性、复现、交付、工程、验证） |
| 位置 | 文件:行/函数，或论文页/公式/表；同类问题可合并写多个位置 |
| 现象与证据 | 读到或运行出的具体事实，含数字；不写形容词 |
| 最小改法 | 按 1..n 步写“改哪个文件、哪个函数/变量、改成什么行为”；不贴可分发的完整代码块 |
| 验收方法 | 改完怎么确认：跑什么、看什么、期望结果是什么 |
| 工作量 | 分钟/小时/天级别的估计，注明是否依赖他人或外部环境 |
| 预期收益 | 解决后消除什么风险（资格风险、结果不可信、无法复现等），可写分数影响但不夸张 |
| 参考依据 | 官方条款编号或权威文档名称与链接；一条足够，不必堆砌 |

> 只给步骤，不给可直接粘贴的代码。允许出现文件路径、函数名、变量名、参数名和验证命令；不允许放成段代码。
> 步骤要写到“一个没看过这份代码的人也能照着做”的程度，但不需要替读者写完整实现。

## 四、报告结构（固定 7 节）

1. **结论与修复顺序**：一共几条、先做哪三条、预计总工作量；一句话说明改完能达到什么状态。
2. **阻断性问题（P0）**：不改就无法提交或结果不可信的问题。
3. **实质问题（P1）**：影响结果可信度、复现或交付的问题。
4. **改进建议（P2）**：工程、可读性、效率类问题；按主题合并。
5. **修复依赖关系**：哪些步骤必须先做（如先补数据入口，再重算结果，再对账）。
6. **验收清单**：把每条的验收方法汇总成可勾选清单；全部通过才算改完。
7. **参考依据与延伸阅读**：官方条款、语言风格指南、可复现性资料的清单。

## 五、排序与合并

- P0 全部排在最前；P1 按“依赖顺序”排（先数据/参数，再算法，再结果，再文档）；P2 最后。
- 同一根因引发多处现象时合并成一条，在“位置”里列全，不要拆成多条重复建议。
- 一个问题既影响资格又影响分数时，按资格红线（阻断）处理。

## 六、写作规则

- 沿用 `报告写作风格_自然专业.md`：结论先行、散文为骨架、说人话。
- 不写“加强规范性、注意鲁棒性、优化代码结构”这类空话；每条必须能勾验。
- 不指责作者；写代码的行为，不写人的问题（Google eng-practices 的惯例）。
- 步骤与验收成对出现；没有验收方法的建议不算完成。
- 工作量、收益是帮助排期用的估计，不写成承诺；不确定时写区间并标注假设。
- 只描述“改什么”，不替读者决定是否重构；若最小修复与理想方案不同，说明最小修复优先，理想方案放可选条目。

## 七、标签写法参考

参考 Conventional Comments 的做法，标签用“类别＋阻断级别”：

- `阻断 · 交付`：缺题目要求的 result*.xlsx，或附录缺完整源程序。
- `阻断 · 复现`：缺输入数据/依赖导致根本跑不起来。
- `非阻断 · 正确性`：局部边界问题，可能污染结果。
- `非阻断 · 工程`：调试残留、命名、重复代码。

## 八、示例（片段）

```
P0-1｜阻断 · 交付
位置：仓库根目录与 problem2_2.py
现象与证据：题目要求 result1.xlsx / result2.xlsx / result4.xlsx，仓库无任何 xlsx；代码只写 verify/ 下 5 个 CSV。
最小改法：
1. 在 src 目录补一个导出脚本，按题目模板的列顺序把现有 CSV 写入 xlsx。
2. 明确三个结果文件对应的问题与数据范围，不要只导出一个。
3. 保留原始模板不动，导出到新文件。
验收方法：运行后仓库出现三份 xlsx；用题目模板逐列核对，行数/列名一致。
工作量：2–3 小时。
预期收益：消除“交付文件缺失”的资格风险。
参考依据：官方 2026 格式规范第五条、第十一条。
```
